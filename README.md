Technical Analysis: Heap Memory Corruption in Android Media Parsing Libraries

Abstract

This document provides an in-depth technical analysis of four heap-based memory corruption vulnerabilities affecting Android media processing libraries. The analysis covers the root cause, the precise code path, the construction of the proof-of-concept (PoC) files, and the observed impact on a Nokia G21 running Android 13. The objective is to document the mechanisms for educational purposes and to assist security teams in testing their media pipelines.

1. WebP Huffman Table Overflow (libwebp)

Root Cause
The VP8LBuildHuffmanTable function in libwebp constructs Huffman tables from a bitstream without adequately validating the aggregate code lengths. The function iterates over the code lengths provided in the bitstream and builds a lookup table. When a crafted VP8L chunk supplies malicious OFFSET and VALUE parameters, the decoder writes beyond the bounds of the allocated heap buffer during table construction.

Detailed Code Path

1. The VP8LDecodeImage function is called when an image is opened.
2. It calls ReadHuffmanCodes to parse the Huffman codes.
3. ReadHuffmanCodes invokes VP8LBuildHuffmanTable for each code group.
4. Inside VP8LBuildHuffmanTable, the function calculates the table size based on the maximum code length.
5. If the maximum code length exceeds the expected limit, the function may write past the allocated buffer.

PoC Construction
The exploit.webp file was generated by modifying the bit-level packing logic in gen_oob_webp.py. The write_bits function was adjusted to use LSB-first ordering, and the OFFSET/VALUE pair was set to 0x1/0x1000 to force a 4KB overflow beyond the expected allocation. The file structure includes a valid RIFF header and a VP8L chunk with manipulated Huffman table data.

Observed Impact
On an unpatched Nokia G21 (Android 13), opening the file in Discord or Google Lens triggers an immediate SIGSEGV in the media decoding thread. The Android runtime terminates the application to prevent further corruption. The vulnerability is confined to the process handling the image; no system-wide compromise occurs.

2. DNG MapTable Integer Overflow (dng_sdk)

Root Cause
In dng_opcode_MapTable::ProcessArea, the addition of fAreaSpec.Plane() and fAreaSpec.Planes() can overflow an unsigned integer. This results in an undersized heap allocation followed by an out-of-bounds write during pixel processing.

Detailed Code Path

1. The DNG file is parsed by dng_validate or a similar decoder.
2. The decoder reads the OpcodeList2 from the DNG file.
3. For each opcode, the ProcessArea function is called.
4. Inside ProcessArea, the AreaSpec is used to calculate the required buffer size.
5. The addition of Plane() and Planes() overflows, leading to a small allocation.
6. The subsequent pixel processing writes beyond the allocated buffer.

PoC Construction
A valid DNG container was generated using pidng. A malicious OpcodeList2 was then injected using inject_opcode.py. The AreaSpec was set to (0, 0, 256, 256) to trigger the overflow path. The file size is approximately 128 KB.

Observed Impact
Opening valid_poc.dng in the Gallery application causes MediaProvider to crash. The issue affects Android 14 and later, but was also observed on Android 13 due to an older dng_sdk version present in the firmware.

3. APV AU_INFO/FRAME Dimension Mismatch (libopenapv)

Root Cause
oapvd_info() reads frame dimensions from the AU_INFO PBU, while oapvd_decode() reads them from the FRAME PBU. A crafted file declares 16x16 in AU_INFO and 64x64 in FRAME, causing a 14,848-byte heap overflow during the decode stage.

Detailed Code Path

1. The media framework parses the MP4 container and extracts the APV bitstream.
2. oapvd_info() is called to retrieve the frame dimensions from the AU_INFO PBU.
3. Based on these dimensions, the framework allocates a buffer.
4. oapvd_decode() is called to decode the FRAME PBU.
5. The dimensions in the FRAME PBU are larger than those in AU_INFO, causing a write beyond the allocated buffer.

PoC Construction
The overflow_auinfo.mp4 file was generated by modifying generate_overflow_mp4.py to set the AU_INFO dimensions to 16x16 and the FRAME dimensions to 64x64. The resulting file is 1,178 bytes.

Observed Impact
No impact on Nokia G21. The libopenapv library is exclusive to Android 16. On an Android 16 device, the file causes a crash in mediaserver.

4. HEIC Tile Dimension Corruption (libheif)

Root Cause
FrameDecoder::onOutputReceived processes HEIC tiles without validating that the calculated tile dimensions are positive. A crafted ispe header with extreme values (e.g., 2048x4095) leads to a negative height, which libyuv interprets as a reflection, resulting in an out-of-bounds write.

Detailed Code Path

1. The HEIC file is parsed by libheif.
2. The ispe box is read to obtain the image dimensions.
3. The decoder calculates the tile dimensions based on the grid.
4. If the calculated height is negative, libyuv processes the data incorrectly.
5. The out-of-bounds write occurs during the pixel copy operation.

PoC Construction
A valid HEIC file was modified using a hex editor. The ispe width and height fields were changed to extreme values to trigger the vulnerable path. The resulting file, poc_crash.heic, is small in size and does not require any additional metadata.

Observed Impact
Opening poc_crash.heic in Google Lens causes a crash in mediaserver due to memory corruption. The application is terminated by the system.

Conclusion

These vulnerabilities are well-documented, but their mechanisms remain relevant for testing unpatched devices. The impact is primarily Denial of Service (DoS) via application crashes. Achieving Remote Code Execution (RCE) would require bypassing SELinux and constructing a ROP chain, which is beyond the scope of this reproduction. Security teams should use this analysis to verify that their media parsers are up to date and that their applications handle malformed files gracefully.
